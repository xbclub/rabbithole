# 判断:default_carriers=2 与 RTT 自适应的冲突(先判断,不改代码)

> 任务要求「先做判断,不要直接改代码」。本文给出判断、依据与推荐方案。
> **截至本文,未修改任何代码。**

## 0. 结论先行

**建议选 A(承认低 RTT 也该 K=2),但理由与任务描述给出的理由不同。**

任务描述里"报告与 round-73 结论相反、未解释冲突"这个前提,**经核实不成立**:

- round-73 比的是 **K=1 vs K=4**,**没有测过 K=2**;
- round-78 的 RTT 曲线在 **0.4ms 那一行 K=2 是 `—`(未测)**,只比了 K=1 与 K=4;
- 报告 §3.1 测的是 **K=1 vs K=2,在 RTT≈0.5ms**,结论 K=2 优(2195→2343)。

所以**没有任何一组数据说"低 RTT 下 K=1 优于 K=2"**。冲突是"拿 K=1/K=4 的实验去推 K=2 的结论"造成的假象,不是真矛盾。

## 1. 三组实验的实际条件(逐条核实)

| 实验 | 对比 | RTT | 直连基线 | 结论 | 证据位置 |
|---|---|---|---|---|---|
| **round-73** | **K=1 vs K=4** | 低 RTT 实验床 | 3.6–4.0 G | K=1 不慢于 K=4(下行快 15–20%) | `lib.rs:451-460` 注释表 |
| **2026-10-20 复测** | **K=1 vs K=2 vs K=4** | 同机房 | 2.6–2.9 G | K=2 优于 K=1(2072→2213),K=4 无额外收益 | `lib.rs:466-472` 表 |
| **报告 §3.1** | **K=1 vs K=2** | **≈0.5ms** | **1713–2686 Mbps** | K=2 优(2195→2343) | `deep-review-performance-report.md:86-93` |
| **round-78 RTT 曲线** | K=1 vs **K=4** | 0.4/10/50/100/300ms | 未注明 | 0.4ms 行:`K=1 3.19` vs `K=4 2.94`,**K=2 未测** | `lib.rs:520-529` |

### 关键发现 1:round-78 的 0.4ms 行缺 K=2

```
| 0.4ms | **3.19** | — | 2.94 | — | K=1 |
                    ↑
                 K=2 未测
```

"最优=K=1"这个标注是**在只测了 K=1 与 K=4 的前提下得出的**,不能用来支持"K=2 比 K=1 差"。

### 关键发现 2:报告 §3.1 恰恰是低 RTT 下 K=2 更优

报告数据:`K=2 后同一扫描(4 流)中位从 2195 → 2343`。测试床 RTT≈0.5ms。

**这已经是"低 RTT + K=2 更优"的直接证据**,而且比任务描述引用的"2195→2343"还要完整。

### 关键发现 3:任务描述里"直连 2.6-2.9G vs round-73 3.6-4.0G"的分歧点是真的,但方向相反

任务描述推测:"载体数收益是否取决于直连可用的绝对带宽(本轮 2.6-2.9G,round-73 是 3.6-4.0G)"。

**若成立,结论应该反过来**:直连带宽**更低**时(2.6-2.9G),单载体更容易成为瓶颈,所以**更该**多开载体。而 round-73 直连 3.6-4.0G 时单载体够用——这正好解释了为什么 round-73 看到 K=1/K=4 无差异,而复测看到 K=2 有收益。**这个推测支持 A,不支持 B。**

## 2. 那"K=1 在 0.4ms 更快"到底还能不能引用?

不能。理由:

1. 它比的是 K=4,不是 K=2;
2. 它的直连基线(3.6-4.0G)比报告测试床(1.7-2.7G)高约 40%,单载体更不容易触顶;
3. 报告 §3.5 明确记为「**载体数越多越好?否。K=4 与 K=2 持平(4 流 2147 vs 2179),只增成本**」——即 K=2 是那个测试床上最好的档。

因此 `carriers_for_rtt` 的 `<5ms → 1` 分支**没有任何数据支持**,它更像是"从 K=4 的实验外推出来的直觉"。

## 3. 现状的真实问题(比任务描述更严重)

任务描述说"低 RTT 时 rtt_k=1,但 proto_baseline=2,max 后恒 2,自适应在低延迟段完全失效"。

核实后确认这个描述**准确**,但需要补充一点:**这不只是"失效",而是"两条规则互相矛盾且没有文档说明谁优先"**。

现状代码(`session.rs:234-241`):

```rust
// RTT 自适应给的是**下限意义上的建议**,不是上限:
// 低 RTT(<5ms)返回 1,但 ... 故取两者较大者,
// 让协议基线抬高下限、RTT 仍能在高 BDP 下继续上调。
rtt_k.max(proto_baseline)
```

注释自己承认了"取较大者",但没说清"为什么 RTT 的建议可以被无声覆盖"。结果是:

- `<5ms`:RTT 说 1,实际 2 → **RTT 分支是死代码**(任务描述正确);
- `5-15ms`:RTT 说 2,实际 2 → 无差异;
- `>=15ms`:RTT 说 4,实际 4 → 唯一真正生效的档位。

即 **`carriers_for_rtt` 实际只在高 RTT 段起作用**,而它的文档(`lib.rs:506-540`)用一整张表论证"低 RTT 该 K=1",与行为不符。

## 4. 推荐方案:A(删掉 <5ms → 1)

### 为什么不是 B

B 要求"用一次三机 A/B 证明低 RTT 下 K=1 更快;若不成立则回到 A"。

但**这个证明已经被报告 §3.1 做过了,结论是反的**(K=2 更优)。再做一次 A/B 的成本很高(三机 + peer.sh 全流程),而预期结果是重复现有证据。

除非能提出一个"报告 §3.1 的测试床不代表生产"的强论据——目前没有。报告测试床是 10GbE 同机房 0.5ms,这已是**对 K=1 最有利**的条件(低 RTT + 高带宽,单窗口最容易够用)。在这种条件下 K=2 还赢,说明 K=1 的劣势不是 RTT 造成的。

### A 的具体改法

1. **`carriers_for_rtt`**:`<5ms` 分支从 `1` 改为 `2`(即 `1` 这个返回值彻底不存在)。
   - 但这会让函数退化成"低 RTT 恒 2、高 RTT 升到 4",**仍保留分段价值**。
2. **`lib.rs:520-529` 的 0.4ms 行**:补注"K=2 未测",并把"最优=K=1"改为"K=1 优于 K=4"——不能让未测值继续被当成结论。
3. **`session.rs:91` 文档**:删掉"低延迟下 K=1 快 8%"的说法(它来自 K=1/K=4 对比)。
4. **`session.rs:234-241` 注释**:改成明确规则——"协议基线是**下限**,RTT 只能在基线上**上调**;当前基线=2,故 RTT 的 <5ms 分支不再存在"。
5. **`baseline_single_for_tcp` / `baseline_single_for_all_protocols`**:名字里的 "single" 与断言 2 矛盾,改为 `baseline_k2_for_*`。
6. **新增测试**:锁住"RTT 建议与协议基线冲突时,取较大者"这一规则(用注入的 RTT 值,断言最终 K)。

### 若最终仍想保留"低 RTT 降到 1"的能力

那必须**先有数据**。建议的最小验证:在报告测试床(0.5ms / 10GbE)上,用 `RH_MUX_POOL_SIZE=1` 与 `=2` 交替各 6–8 轮,4 流与 16 流各一遍。若 K=1 稳定不慢于 K=2,才回到 B。
