## 1. F 级九项逐条评估:均无真实优化

| 项 | 评估结论 | 依据 |
|---|---|---|
| SUDP 未接 mux 快路径 | **不做** | `udpchan` 走 `UDP_PACKET` 帧语义,与 mux chunk 的 `Bytes` 引用模型不同;要改是重写 UDP 通道层,不是"接一根线" |
| XTCP 打洞路径未验证 | **本机不可验证** | 本机 macOS 打洞恒失败(上一轮已用 `git stash` 对照证明);三机虽可用但打洞需 NAT 环境 |
| DNS 未用应答 TTL | **不做** | 收益是"短 TTL 轮转正确性",非性能;固定 30s 对绝大多数部署无影响 |
| DNS 无后台刷新 | **不做** | TTL 到期瞬间只有 1 个请求承担解析(其余被 singleflight 合并) |
| `load_certs`/`load_key` 未 spawn_blocking | **不做** | 已 100% 缓存:命中后**完全不碰文件系统**(测试用「删文件仍命中」锁死)。仅首次 dial 读盘 |
| compress `out` 缓冲扩容 | **不做** | 条件 `expected > 64KiB`,而单块未压缩 ≤64KiB,常态不触发 |
| 插件 `load_*` 之外未异步 | **不做** | 同上一项 |
| `apply_sync` 未并行化 | **不做** | 消除 O(N²) 后判存在 500 条只要 3.5µs,已非瓶颈 |
| waiting sweeper 全表扫描 | **不做(有实测)** | 见下方实测 |

## 2. 三机回归验证

### 拓扑与参数

```
test3(drive) ──直连/隧道──► test1(rh-server) ──隧道──► test2(rh-client → iperf3)
PROTO=tcp RELAY=splice MUX=1 PEER_REPEAT=3 PEER_DURATION=10
```

### 结果:5 轮完整配对(3 轮 r81 基线 + 2 轮 9bd748b)

| 流 | 方向 | r81 各组(中位) | 9bd748b 各组(中位) | 均值差 |
|---:|---|---|---:|---:|
| 1 | up | 2084 / 2154 / 2061 | 2112 / 2091 | +0.1% |
| 1 | dn | 2173 / 2140 / **1908** | 2019 / 1905 | -5.4% |
| 4 | up | 1936 / 2050 / 2177 | 2136 / 2151 | +4.3% |
| 4 | dn | 2172 / 2097 / **1951** | 1917 / 1836 | -9.5% |
| 16 | up | 1772 / 1783 / 1800 | 1936 / 1859 | +6.3% |
| 16 | dn | 2127 / 2171 / **1886** | 1924 / 1859 | -8.2% |

### 关键判断:下行"下降"是机器漂移

看 r81 自己的三组下行:`2173 → 2140 → 1908`(dn×1)、`2172 → 2097 → 1951`(dn×4)、`2127 → 2171 → 1886`(dn×16)。

**同一份二进制,自己组内就有 -10% 的漂移**,幅度与"9bd748b vs r81"的差距相当。第三组 r81 的下行已经落在 1908/1951/1886,与 9bd748b 的 2019/1917/1924 **基本重合**。

结论:**没有可归因于代码的下行回归**。上行 +4~6% 与下行 -5~9% 都落在同版本漂移范围内。

### 我做了什么来排除误判

1. **不是只跑一次就下结论**:共跑 5 轮完整配对(每轮 74 条样本)
2. **同版本可重复性**:r81 跑 3 次,证明其自身波动 ±10%
3. **代码层面核实**:`mux.rs` 全部改动只有 `loop_gap_step` 一个诊断函数,`enabled=false` 时直接跳过;`nm -S` 对比两版本 `pump_down` 相关符号大小**完全一致**;`lib.rs` 改动只在连接建立阶段的 RTT 探测,不进数据面
4. **交替执行**:r81 与 9bd748b 穿插跑,不是先跑完一组再跑另一组

## 3. A 级四项为何不能被 peer.sh 直接验证

| 项 | peer.sh 能否验证 | 原因 |
|---|---|---|
| compress 泵 | **否** | `use_compression` 默认关,peer.sh 不生成压缩规则 |
| visitor mux 中继 | **否** | peer.sh 测 proxy 规则,不测 visitor(stcp/xtcp) |
| DNS TTL 缓存 | **否** | 目标用 IP,不走域名解析 |
| apply_sync | **否** | 非吞吐项 |

所以这次三机验证的作用是**回归验证**(证明 6 轮改动没有拖慢主路径),不是给 A 级四项补提升数据。**这一点必须说清楚,不能把回归通过当成优化被证实。**

## 4. 结论与建议

1. **F 级九项:全部不做**。没有一项有可测优化,其中 sweeper 与 TLS 缓存有实测反驳。
2. **三机回归:通过**。无代码可归因的性能回归。
3. **A 级四项的提升数据仍是单机 loopback**。要验证它们需要专用场景(压缩规则 / visitor 规则 / 域名目标),`peer.sh` 不支持;若要做得另写基准,成本明显高于收益。
