# 单载体/多载体瓶颈实测结论(2026-10-18)

> **状态:参考**。本文从 85 轮实验日志(13,119 行,已随 2026-10-22 整理删除)
> 中抽出**仍然有效的结论**。原始日志可用 `git log --diff-filter=D -- docs/single-carrier*` 取回。
>
> 这些结论**支撑了 `README.md` 里多载体定容规则的取值**,但 README 只写了
> "是什么",本文解释"为什么"。

---

## 1. 首要结论:"必须多载体才能达到 frp 水平"是错的

K=1 单载体即可达到甚至超过 frp,**多载体的收益完全取决于 BDP**。

早期假设"×16 时单核软中断打满,所以必须多载体"被实验证伪:

| 指标 | K=1、×16 下行 |
|---|---|
| 服务端进程 CPU | **0.74 核**(8 个 tokio worker 均匀分布,最高单线程 0.13 核) |
| 内核软中断 NET_RX | 分散在 **7/8 个核**,最大核 29.7% |
| 每核 busy | 6.8% ~ 11.5% |

**没有任何核接近饱和。** 瓶颈不是 CPU、不是软中断、也不是载体数量。

---

## 2. 多载体的收益条件:看 BDP

实测曲线(下行 P=16,中位 Gbps):

| RTT | K=1 | K=2 | K=4 | K=8 | 最优 |
|---|---:|---:|---:|---:|---|
| 0.4ms | **3.19** | — | 2.94 | — | **K=1** |
| 10ms | **3.52** | 3.32 | 3.59 | — | K=1/K=4 持平 |
| 50ms | 1.82 | 2.24 | 2.50 | **2.60** | K=8 |
| 100ms | 1.20 | 1.72 | **2.10** | 1.96 | **K=4** |
| 300ms | 0.70 | 0.84 | **0.75~0.83** | 0.50 | **K=4** |

**两条反直觉的结论:**

1. **低延迟下 K=1 更快**。0.4ms 时 K=1 比 K=4 快 **8.4%**(15 轮配对,
   中位 3.188 vs 2.941,K1 胜 11/15,95% CI 不含 0)。
2. **高延迟下 K 不是越大越好**。300ms 时 K=8 比 K=4 **慢 33%**(0.501 vs 0.748),
   甚至不如 K=2(0.84)。

K 过大的代价:每条载体分到的并发流太少(16 流 ÷ 8 载体 = 每载体仅 2 条),
且 `FlushTask` 只聚合自己那几条流,写系统调用被摊薄。

> **与现役代码的关系**:`default_carriers()` 现在对所有协议返回 **2**
> (QUIC/KCP 为 1)。其注释记录的依据是 2026-10-20 的三机 A/B:
> K=1 时 4 流 2072 / 16 流 2178;K=2 时 2213 / 2306;K=4 与 K=2 持平
> (2184 / 2323)「只增成本」。**单载体在 2.1-2.2 G 封顶且与流数无关**,
> 瓶颈是 yamux 发送侧单 `FlushTask` 串行 + 单 TCP 流的拥塞窗上限,
> 不是 CPU(服务端仅 0.26 核)。
>
> 注意:本文 §2 的曲线测于低 RTT 实验床(0.4ms),当时直连上限约 3.2G;
> 而 `default_carriers` 的依据是直连可达 2.6-2.9G 的另一批实验。
> **两批结论方向一致(K 增大到某点后无收益),但绝对数值不可直接混用。**

## 3. 机制:为什么多载体在低延迟下反而慢

`perf record` 定位(K=4,下行 P=16,服务端):

```
95.08%  do_syscall_64
        48.48%  __x64_sys_writev → tcp_sendmsg
                46.21%  copy_user_generic_unrolled   ← 用户/内核数据拷贝
        43.94%  __x64_sys_recvfrom → tcp_recvmsg
                25.19%  __skb_datagram_iter → skb_copy_datagram_iter
```

每字节归一化指标(不随带宽漂移,稳定可比):

| 指标 | K=1 | K=4 |
|---|---:|---:|
| `ticks/GB` | 341~378 | 387~416(**+11~12%**) |
| `syscw/GB` | 1534~1832 | 2293~3388(**+1.5~1.9×**) |
| 平均单次 `writev` | **589 KiB** | **384 KiB** |

**K=4 把单次写入从 589 KiB 摊薄到 384 KiB**,写调用次数涨 1.5~1.9 倍,
`ticks/GB` 在 4/4 轮里都更高。低延迟下这部分固定开销无法被窗口收益抵消。

## 4. 与 frp 的对比:延迟越高,优势越大

frp 侧 `poolCount=4`(静态)、`tcpMux=true`;rh 走 RTT 自适应不设 `RH_MUX_POOL_SIZE`。

| RTT | rh | frp | rh/frp |
|---|---:|---:|---:|
| 0.43ms | 3.50 | 2.37 | **1.48×** |
| 50ms | 3.46 | 1.38 | **2.51×** |
| 100ms | 2.44 | 0.73 | **3.34×** |
| 300ms | 0.130 | 0.033 | **3.94×** |

原因:frp 的载体数是**静态配置**,不随 RTT 调整;rh 在每个 RTT 档位都选到
自己实测的最优 K(低延迟 K=1 避免分摊损失,高延迟 K=4 吃满窗口收益)。
高延迟下这个差异被放大。

> 300ms 档须用 30s 长跑测量:12s 短跑时 K=4 的四条载体还在慢启动,
> 噪声过大(曾因此得出错误结论)。

## 5. 多客户端并发:不互相拖累

低延迟(0.43ms),两客户端各选 K=1:

| 场景 | 吞吐 |
|---|---:|
| 单路(两客户端空闲) | 2.82 G |
| 两路并发 A / B | 1.85 / 1.86 G |
| **两路合计** | **3.70 G** |

合计 3.70 G > 单路 2.82 G —— 并发反而更充分利用链路(单路受限于单条 TCP
的窗口与聚合效率)。

高延迟(150ms),两客户端各 K=4(共 8 条连接):单路 0.90 G,两路合计 1.19 G。
每路降到 0.6 G 是**共享同一条出口的正常表现**,不是多载体的缺陷。

> **测试陷阱**:服务端对新 `client_id` 有准入检查(`state.db.get_client`),
> 未在 DB 注册的连接会被拒(`AUTH_FAILED: unknown client`)。早期"起了两个
> 客户端"的测试因此全部无效——实际只有一个连上。注册方式(测试用):
> ```sql
> INSERT INTO clients (id,name,secret,remark,created_at)
> VALUES ('bench-client-002','bench2','<secret>','',<now_ms>);
> ```

## 6. 被证伪的方向(不要再试)

| 方向 | 结论 |
|---|---|
| 单核软中断打满 | 证伪:NET_RX 分散 7/8 核,最高 29.7% |
| 目标侧(目标服务)瓶颈 | 目标仅 0.22 核 |
| 分片通道容量不足 | +3.5%,噪声内 |
| 上下行锁竞争 | 上行等待仅 2758B |
| 块大小不当 | 块全程恒定 64KiB |
| cwnd 窗口受限 | 推翻(Round-8) |
| 放大帧大小 | 帧大小**不是**主导变量(注:该轮曾把变量设在客户端,设错了机器,结论已更正) |
| 提高并发数(P=64)让多载体翻盘 | CI 跨 0,无效 |

**真正的方向**:应用层写入节奏 / 下行预取深度 / 每载体 FlushTask 的聚合效率。

## 7. 方法论教训(仍有效)

1. **绝对吞吐会漂移,用每字节归一化指标**。站点带宽从 3.15G 掉到 2.4G 时,
   `ticks/GB` 与 `syscw/GB` 仍稳定可比。
2. **短跑会骗人**。300ms 档用 12s 测出的结论是错的(慢启动未完成)。
3. **配对样本 + CI**。15 轮配对、95% CI 不含 0,才能说"8.4% 的差距是真的"。
4. **设错机器的变量会让整轮结论无效**。`RH_UP_CHUNK_CAP` 是服务端变量,
   设在客户端后那轮扫描全废。
5. **多客户端测试必须先注册 client_id**,否则只有一个连上。
