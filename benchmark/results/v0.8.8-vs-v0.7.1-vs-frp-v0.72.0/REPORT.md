# rabbithole v0.8.8 vs v0.7.1 vs frp v0.72.0 官方 Release 三方同场实测(2026-11-24)

## 1. 测试方法修复与环境校验

本结果集使用重写后的全 Go 压测器 [`benchmark/loadgen`](../../loadgen)（commit `0e75adf`）在连续相邻三轮中完成同场采集，彻底消除了此前工具链中的三处失真：
1. 移除吞吐 `sink`/`src` 显式 `SetReadBuffer(4MiB)`/`SetWriteBuffer(4MiB)`，恢复 Linux `tcp_moderate_rcvbuf` 自动调谐（单流直连从 ~`1.15 Gbps` 假天花板恢复至真实的 **`2.66–3.05 Gbps`**，彻底消除单流 `>100%` 假保留率）；
2. 实现 `-R` 真双向 `download`（此前 `loadgen` 下行实为单向发送，`loadgen sink` 与每连接独立 `256 KiB` 缓冲 + 局部统计，消除锁/伪共享）；
3. 以 Go `loadgen target`（`net/http` 自动 `TCP_NODELAY` 与头体合写 + `SO_REUSEPORT` UDP 多协程回显）及 Go 压测子命令取代 Python `loadgen.py` / `target.py`（消除 HTTP 40ms 延迟 ACK、GIL 限制与 4096 并发 Python `selectors` 假瓶颈）。

- **测试时间**：2026-11-24 10:04–11:10 UTC（连续三轮，三机 8 核 Xeon E5-2680 v3 / 10GbE VMware，Linux 5.15.0-203）
- **被测产物**（均取自 GitHub 官方 Release 并通过 SHA-256 校验，完整哈希见 [`SHA256SUMS.txt`](SHA256SUMS.txt)）：
  - **rabbithole `v0.8.8`**（`x86_64-unknown-linux-musl`）
  - **rabbithole `v0.7.1`**（`x86_64-unknown-linux-musl`）
  - **frp `v0.72.0`**（`linux_amd64`，2026-11-04 发布）
- **配置对齐**：控制面 `tcp`、`multiplex=true`/`tcpMux=true`、`pool_size=4`/`poolCount=4`、压缩关闭、`relay_mode="splice"`、`nofile=65535`。
- **无效样本**：**0**（`v0.8.8` 102 条记录、0 坏行；`v0.7.1` 102 条记录、0 坏行；`frp v0.72.0` 全部 0 错 / 0 零值）。

### 单流性能定位结论

此前旧 Go/Python 混测轮次误报“单流下行 `v0.8.8` 1523 Mbps 落后 `frp` 1804 Mbps”，经去伪影三方同场对照已完整定位：
1. **代码无单流性能退化**：`v0.8.8` 与 `v0.7.1` 单流区间完全重叠——上行同为 `[2055..2553]`（中位 `2174` vs `2361`，双峰采样波动）、下行几乎完全一致（`1960` vs `1947`，`1.007×`），且 `v0.8.8` 全程服务端与客户端上行单核 CPU 反而降低 `5.7%–13.8%`。
2. **真双向口径下 `rabbithole v0.8.8` 单流全面领先 `frp v0.72.0`**：在真实的 `2.8–3.0 Gbps` 单流直连基线下，`v0.8.8` 保留率为 `72.3%`，显著高于 `frp v0.72.0` 的 `52.8%–55.5%`（上行 **+38.5%**、下行 **+12.4%**）。此前旧测试的“落后”完全源自 `loadgen sink SetReadBuffer(4MiB)` 造成的 cwnd 塌陷伪影与假下行采样。
3. **16 流为什么超过直连基线**：本拓扑为 VMware 8 核虚拟化 10GbE，16 条裸直连并发在单机 NIC/softirq 与多线程 `src/sink` 调度下约在 `2.55–2.77 Gbps`，而 `rabbithole`（以及 `frp` 下行 `3055`）通过连接池/yamux 在 `K=2–4` 条长载体连接上做大帧聚合写，减少了内核套接字调度与小包系统调用，可达 `3.26–3.31 Gbps`。
