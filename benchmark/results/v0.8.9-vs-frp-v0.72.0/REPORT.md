# rabbithole v0.8.9 vs frp v0.72.0 官方 Release 同场实测(2026-11-25)

## 1. 测试配置与产物校验

本结果集使用纯 Go 压测器 [`benchmark/loadgen`](../../loadgen)（commit `0e75adf`，`-R` 真双向 `download`、无 `SetReadBuffer` 伪影、无 Python 瓶颈）在相邻时间窗完成官方 Release 同场实测（全档直连基线偏差仅 `-9.6%..+6.2%`）：

- **测试时间**：2026-11-24 23:50 UTC（`frp v0.72.0`）与 2026-11-25 00:22 UTC（`rabbithole v0.8.9`），三机 8 核 Xeon / 10GbE VMware，Linux 5.15.0-203
- **被测产物**（均取自 GitHub 官方 Release 并通过 SHA-256 校验，完整哈希见 [`SHA256SUMS.txt`](SHA256SUMS.txt)）：
  - **rabbithole `v0.8.9`**（`x86_64-unknown-linux-musl`）
  - **frp `v0.72.0`**（`linux_amd64`，2026-11-04 发布）
- **配置对齐**：控制面 `tcp`、`multiplex=true`/`tcpMux=true`、`pool_size=4`/`poolCount=4`、压缩关闭、`relay_mode="splice"`、`nofile=65535`。
- **无效样本**：**0**（`rh-v0.8.9` 102 条记录、0 坏行；`frp-v0.72.0` 70 条记录、0 错 / 0 零值）。

| **4 流下行** | 2656 / 2729 `[2729,2982,2732,2564,2508]` | 2755 / **2908** `[2908,2956,3043,2852,2893]` | 102.7% | 103.5% | 0.938× (−6.2%) |

- **`v0.8.9` 相对 `frp v0.72.0` 拿下 5/6 档位**，包括关键的 **1 流（上行 `+57.2%` / 下行 `+15.8%`）**、**4 流上行（`+10.6%`）** 与 **16 流双方向（上行 `+21.1%` / 下行 `+9.3%`）**；仅 `4 流下行`（`2729` vs `2908 Mbps`）略低于 `frp`（`0.938×`，较 2026-11-24 `v0.7.1` 的 `2558 Mbps` 仍高 `+6.7%`）。
- **多流超过裸直连的原因**：在 VMware 8 核虚拟化 10GbE 环境下，`4–16` 条裸直连并发在单机 NIC/softirq 下约达 `2.44–2.77 Gbps`，而 `rabbithole` 通过 `K=2` 条长期载体做聚合大帧写（`v0.8.9` 新增按 `proxy_id` 作用域均衡分派，消除早先多规则交错 warmup 导致的 `3+1`/`4+0` 倾斜，实测两载体各载 `~75–81 GB` 严格均衡），吞吐稳居 `3.07–3.32 Gbps`。

### 3.3 并发连接(`64 / 256 / 1024 / 4096`)

rabbithole `v0.8.9` 跑 **3 轮**（`PEER_CONC_REPEAT=3`），frp 跑 **1 轮**（`hold=5s`），双方全部档位 `established = verified = hold_alive = N`（**0 失败**）：

| 并发 | v0.8.9 直连 / **隧道建连 p99** (3 轮) | v0.8.9 **隧道 PING/PONG 校验 p99** | frp 直连 / 隧道建连 p99 | frp 隧道校验 p99 |
|---:|---|---|---|---:|
| 64 | 28.6 / **27.2 ms** `(16.0, 29.7, 27.2)` | **19.0 ms** `(16.9, 19.0, 19.6)` | 2.8 / **3.6 ms** | 46.3 ms |
| 256 | 36.0 / **37.8 ms** `(83.5, 34.0, 37.8)` | **36.5 ms** `(58.9, 36.5, 34.7)` | 23.9 / **30.5 ms** | 131.5 ms |
| 1024 | 127.6 / 199.6 ms `(165.4, 230.6, 199.6)` | **113.9 ms** `(113.9, 178.7, 113.3)` | 113.1 / **121.4 ms** | 517.0 ms |
| 4096 | 224.1 / 589.0 ms `(589.0, 659.6, 504.8)` | **332.4 ms** `(269.7, 463.0, 332.4)` | 144.4 / **206.7 ms** | 820.6 ms |

- **listen backlog=4096 彻底消除 1 秒 SYN 重传毛刺**：在 2026-11-24 的 `v0.8.8` 实测中，4096 并发突发因服务端 listen backlog=128 在第 2/3 轮触发 `1028.3 / 1060.6 ms` Linux 1 秒 SYN 重传；`v0.8.9` 将全栈 TCP listen backlog 抬至 4096 后，3 轮 `4096c` 建连 p99 稳定收敛至 `504.8–659.6 ms`（0 例秒级毛刺）。
- **应用层端到端握手校验延迟（`verify_rtt p99`）全档领先 frp**：在 4096 并发下完成真实 PING/PONG 往返校验的 p99 仅 **`332.4 ms`**，为 frp（`820.6 ms`）的 **`2.47×` 更快**；`1024c` 下为 `113.9` vs `517.0 ms`（**`4.54×` 更快**）。
